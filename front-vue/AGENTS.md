# pc-pure 开发约定

这份文档是给人和 AI 一起用的。开始写代码前，先读完它，再动手。

## 1. 项目定位

- 这是一个 Vue 3 + Vite + Pinia + Vue Router + Element Plus 的 PC 管理端起步框架。
- 默认使用 Composition API 和 `<script setup>`。
- 没有明确收益时，不要引入新状态库、新请求库、新工具库。
- 业务代码优先保持“薄页面 + 清晰组件 + 小型工具函数”的结构。

## 2. Vue 编码规则

- 组件一律优先用 `<script setup>`，不要新增 Options API 组件。
- 页面组件负责组装，不负责堆满业务细节；复杂逻辑应下沉到子组件或 composable。
- 组件通信坚持 `props down / events up`，不要让子组件直接改父组件状态。
- 模板里不要写复杂计算、过滤、排序；这些逻辑放到 `computed` 或工具函数里。
- 样式顺序保持为：`<script>` -> `<template>` -> `<style scoped>`。
- `scoped` 样式优先用 class 选择器，不要依赖裸标签选择器。

## 3. 响应式适配约定

参考 `CardGame-admin` 的成熟做法，后续 `pc-pure` 新页面都按下面的规则写：

- 断点统一使用三档：
  - `>= 1200px`: 宽桌面，允许多列信息和更舒展的卡片布局
  - `768px - 1199px`: 平板/小桌面，优先压缩间距和列数
  - `<= 767px`: 手机布局，表格改卡片、表单标签改顶部、弹窗宽度贴近视口
- 手机态不是简单缩放，而是结构降级：
  - 表格优先切卡片视图
  - 表单 `label-position` 改为 `top`
  - 弹窗宽度优先用 `calc(100vw - 24px)`
  - 详情展示优先把 `el-descriptions` 的 `column` 改成 `1`
- 页面容器优先拆成两层：
  - 页面层：负责标题、操作区、整体节奏
  - 区块层：负责单块内容卡片、表单、列表、统计区
- 全局间距建议：
  - 桌面端主间距 `16px`
  - 平板/移动端主间距 `12px`
- 全局字号和 Element Plus 组件尺寸应通过 CSS 变量统一收口，不要在页面里到处写零散魔法值。

## 4. 推荐的页面骨架

- 页面根节点使用单一页面容器类，例如 `.page-container`。
- 页面头部拆出标题区和 actions 区，移动端改成上下堆叠。
- 内容区域优先使用卡片区块，不要把所有内容直接裸堆在页面根节点。
- 列表页默认结构：
  - 筛选区
  - 数据区
  - 分页区
- 表单页默认结构：
  - 说明区
  - 表单区
  - 提交操作区

## 5. 网络层约定

- 所有接口统一走 `src/utils/request.js`。
- 不要在业务页面里直接写 `axios.create()`、重复写 token 注入、重复写错误提示。
- 401 或登录失效，统一交给请求层处理。
- 业务接口函数放到 `src/api/*`，页面里只调用 API 方法，不直接拼请求配置。

## 6. 状态管理约定

- Pinia store 保持聚焦，一个 store 只解决一个明确领域。
- store 中允许放状态、派生状态、领域动作；不要把页面特有的展示逻辑塞进 store。
- 默认状态要可重置，推荐抽离初始化对象并复用重置逻辑。

## 7. 工具函数约定

- 小而稳定的通用逻辑，放到 `src/utils`。
- 不再新增 `lodash` 依赖，优先复用 `src/utils/myLodash.js`。
- 高频工具先使用：
  - `debounce`
  - `throttle`
  - `cloneDeep`
- 如果后续要新增工具函数，先确认是否真的跨模块复用，再加到 `myLodash`。

## 8. 样式约定

- 全局样式只放 reset、token、排版基线、通用动画和少量通用工具类。
- 页面/组件样式优先局部化，不要把业务样式塞进全局 CSS。
- 不要默认写死 `100vh`，优先兼容 `100dvh`。
- 避免随手隐藏所有滚动条；只有明确视觉需求时才局部处理。

## 9. 文件组织约定

- `src/api`: 所有接口封装
- `src/store`: Pinia store
- `src/components`: 跨页面复用组件
- `src/views`: 页面级组件
- `src/utils`: 无状态工具函数
- `src/composables`: 可复用的响应式逻辑

## 10. 给 AI 的执行规则

- 新增页面前，先想清楚页面容器、区块组件、数据流，不要直接写成一个大文件。
- 修改现有文件时，优先延续当前风格，不要半路切另一套模式。
- 新增响应式逻辑时，先判断是否只需 CSS 断点；只有确实涉及结构切换时，再引入 `isMobile` 一类的响应式状态。
- 新增工具函数时，保持 API 简单，优先解决当前项目真实场景。
- 除非明确必要，不要引入体积较大的第三方工具库。

## 11. 本轮已经确定的基础约束

- `lodash-es` 已经准备移除，统一改用 `src/utils/myLodash.js`
- 请求层已经统一到 `src/utils/request.js`
- 后续如果补响应式基础设施，优先抽：
  - `useResponsive`
  - `useAppStore`
  - `theme.css`
